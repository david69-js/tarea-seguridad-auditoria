1. Descripción de las pruebas

Se aplicó el proceso de pruebas de software sobre el proyecto POS Web de la Tienda Bugambilias, documentando un caso en el Formato de Caso de Prueba Estándar por cada módulo evaluado: Ventas, Ingreso de Usuarios (Autenticación) e Ingreso de Producto (Gestión de Productos). Cada caso documentado está respaldado por pruebas automatizadas que se ejecutan sobre el sistema en funcionamiento.

  • Herramienta: Jest 29 (Node.js 20), ejecutando los casos contra la API REST real (PHP 8.3 + MySQL 8).
  • Entorno: aplicación levantada con Docker Compose en http://localhost:8091; base de datos pos_tienda con datos de ejemplo.
  • Usuarios de prueba: admin@tienda.com / admin123 (administrador).
  • Comando de ejecución: cd pruebas && npm install && npm test
  • Tipos de prueba: caja negra (contra el requerimiento) y caja gris (se conoce parte del diseño interno y se prueba desde la API).

2. Casos de prueba (formato estándar)

Caso 1 · Módulo VENTAS   Caja negra

Archivo de prueba: pruebas/ventas.test.js — Endpoint: POST /api/ventas
ID del caso de pruebaCP-VENTA-001
Escenario de pruebaRegistrar una venta correctamente: calcula el total y descuenta el stock.
Pasos de la prueba 1. Iniciar sesión como administrador.
2. Registrar un producto con precio de venta Q14.00 y stock 20.
3. Enviar POST /api/ventas con items: [{ id_producto, cantidad: 2 }].
4. Consultar el producto para verificar el stock resultante.
Requisitos previosSesión activa con rol administrador; el producto existe, está activo y tiene stock suficiente.
Datos de pruebaProducto: código VEN-(único por corrida) · precio de venta Q14.00 · stock 20.
Venta: 2 unidades, sin descuento.
Resultado esperado / previsto201 Created con el mensaje «Venta registrada correctamente.»; total = Q28.00 (2 × Q14.00); estado «completada»; el stock baja de 20 a 18.
Resultado real201 «Venta registrada correctamente.»; total 28; estado «completada»; el stock del producto quedó en 18.
Estado de la pruebaAprobado

4. Criterios de aceptación

  • Un caso se aprueba cuando el resultado real coincide con el esperado (código HTTP, mensaje y datos).
  • El módulo se acepta si el 100 % de sus casos quedan aprobados y no hay defectos críticos abiertos.
  • Ante un fallo se registra el defecto, se corrige y se vuelve a ejecutar la suite completa (regresión).
